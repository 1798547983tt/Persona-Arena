# 0009 原著整理成「幕 → 剧情点」，罗盘先定位再推演

日期：2026-09-25 · 状态：已采用（取代 ADR-0005 中"TXT 逐段提要再汇总成一份梗概"的做法）

## 背景

原先 TXT 小说的处理是 map-reduce：每 6000 字提要一段，再反复压缩成一份不超过 5000 字的梗概。用户反馈五百万字的小说被压成三千多字，中后期剧情几乎全丢，罗盘也无从判断故事进行到哪里。

## 决定

- 原著 = 一份概览 + **幕目**。幕目是按阶段划分的若干**幕**，每幕若干条**剧情点**（15–40 字一条的事实），加标题、概述与主要人物。
- TXT 流水线：逐段提取剧情点（可并发，断点续跑）→ 每 N 段合并成一**节** → 模型按阶段把节划分成幕（幕数约为节数 / 6，连续覆盖、不重叠）→ 剧情点超过 40 条的幕再整理压缩 → 由幕目写概览。信息量随篇幅线性增长，而不是被压到固定长度。
- "按作品名生成"直接让模型输出 JSON 的概览 + 幕目；手写 / 世界书原著可一键"自动分幕"。
- 推演前先**定位**：把幕目摘要与最近正文交给模型，判断当前在第几幕、进行到哪个剧情点、依据与置信度；导演可手动指定当前幕。罗盘只拿到"本幕全部剧情点 + 上一幕末尾要点 + 下一幕剧情点"，而不是整本书。
- 幕目可手改、增删、导出为 `.canon.json`、导入。
- 存放：索引与概览在设置里；幕目 JSON 不超过 8 万字时也放进设置（酒馆设置存在服务端，跨设备可用），更大时只存浏览器 IndexedDB；原文和总结进度只存 IndexedDB。

## 理由

- 幕 / 剧情点是编剧的自然单位；"当前在哪一幕"也正是同人推演最需要的坐标。
- 分层让长篇也能保留完整脉络，而单次请求的提示词长度仍受控（罗盘只看三幕）。
- 定位与推演分开，定位只需很少 token，可以单独重跑，也方便导演纠正。

## 代价

- 百万字约 200 次请求，五百万字约 1000 次；因此支持并发、中止与续跑。
- 幕目太大时不跨设备；提供导出 / 导入文件补救。
